# Lab 01 — Driver Installation and Verification

## Objective

Verify the complete Linux driver stack used by the Alfa AWUS036ACH, check for
conflicting third-party modules, inspect firmware initialization and confirm
that the driver can be safely unloaded and reloaded.

No third-party driver was installed because Ubuntu already supplied a working
in-kernel driver.

## Test Environment

| Item | Observed value |
|---|---|
| Kernel | `6.17.0-40-generic` |
| USB ID | `0bda:8812` |
| Chipset | Realtek RTL8812AU |
| Primary driver | `rtw88_8812au` |
| Firmware | `52.14.0` |
| USB path during test | `4-2` |
| USB speed | `5000` Mbit/s |
| USB power control | `on` |
| Network manager | NetworkManager |
| Interface state | Disconnected |

The public documentation omits the complete MAC address and local SSID.

## 1. Confirming Hardware Presence

The device was detected with:

```bash
lsusb -d 0bda:8812
```

Relevant result:

```text
Realtek Semiconductor Corp. RTL8812AU 802.11a/b/g/n/ac 2T2R DB WLAN Adapter
```

## 2. Loaded Driver Stack

The loaded modules were inspected using:

```bash
lsmod | grep -E '^(rtw88|8812au)'
```

The active stack was:

```text
rtw88_8812au
rtw88_8812a
rtw88_88xxa
rtw88_usb
rtw88_core
```

The layers have the following roles:

| Module | Role |
|---|---|
| `cfg80211` | Linux wireless configuration API |
| `mac80211` | Software implementation of the Wi-Fi MAC layer |
| `rtw88_core` | Common Realtek RTW88 driver logic |
| `rtw88_88xxa` | Common RTL88xxA-family support |
| `rtw88_8812a` | RTL8812A chipset-specific support |
| `rtw88_usb` | USB transport support |
| `rtw88_8812au` | RTL8812AU USB device driver |

Module dependencies were inspected with:

```bash
modprobe --show-depends rtw88_8812au
```

## 3. DKMS Conflict Check

Third-party kernel modules were checked using:

```bash
dkms status
```

Only VirtualBox DKMS modules were installed. No third-party `8812au`,
`rtl8812au` or conflicting Realtek DKMS driver was present.

This is important because installing a vendor or community driver alongside
the in-kernel driver can create ambiguous device binding, build failures after
kernel upgrades or inconsistent behaviour.

## 4. Driver Binding

The driver bound to the interface was verified through sysfs:

```bash
ALFA_IF=<alfa-interface>
readlink -f "/sys/class/net/$ALFA_IF/device/driver"
```

Result:

```text
/sys/bus/usb/drivers/rtw88_8812au
```

This confirms that the interface was controlled by `rtw88_8812au`.

## 5. Firmware Initialization

Kernel messages were inspected using:

```bash
sudo journalctl -k -b --no-pager |
    grep -iE 'rtw88|8812au|0bda'
```

Relevant initialization message:

```text
Firmware version 52.14.0, H2C version 0
```

Although `ethtool -i` reported `firmware-version: N/A`, the kernel log showed
that firmware version `52.14.0` was loaded. The `ethtool` value therefore meant
that the driver did not expose the firmware version through that interface; it
did not mean that firmware was absent.

## 6. USB Power State

The USB path and power state were checked with:

```bash
USB_PATH=$(basename "$(readlink -f "/sys/class/net/$ALFA_IF/device")" |
    cut -d: -f1)

cat "/sys/bus/usb/devices/$USB_PATH/power/control"
cat "/sys/bus/usb/devices/$USB_PATH/power/autosuspend"
cat "/sys/bus/usb/devices/$USB_PATH/speed"
```

Observed values:

```text
control: on
autosuspend delay: 2
speed: 5000
```

`power/control = on` means runtime autosuspend was disabled for the device.
Consequently, the configured two-second autosuspend delay was not active.

## 7. Controlled Driver Reload

The device-specific driver was unloaded:

```bash
sudo modprobe -r rtw88_8812au
```

After unloading:

- The USB device remained visible through `lsusb`.
- The Alfa wireless interface disappeared.
- The internal Intel Wi-Fi interface remained connected.
- Shared RTW88 modules could remain loaded without indicating an error.

The driver was loaded again:

```bash
sudo modprobe rtw88_8812au
```

After reloading:

- Firmware `52.14.0` initialized successfully.
- The Alfa interface returned.
- The MAC-based interface name remained stable.
- The PHY number changed from `phy13` to `phy14`.
- No initialization failure appeared in the kernel log.

This confirmed that the driver could be unloaded and reinitialized cleanly.

## 8. Module Compatibility and Signing

Module metadata was inspected with:

```bash
modinfo -F vermagic rtw88_8812au
modinfo -F signer rtw88_8812au
modinfo -F alias rtw88_8812au | grep -i 'v0BDAp8812'
```

Observed values:

```text
vermagic: 6.17.0-40-generic SMP preempt mod_unload modversions
signer: Build time autogenerated kernel key
alias: usb:v0BDAp8812d*dc*dsc*dp*icFFiscFFipFFin*
```

The matching `vermagic` confirms compatibility with the running kernel. The
USB modalias maps Realtek vendor `0bda` and product `8812` to this driver,
allowing automatic loading when the adapter is connected.

## Key Findings

1. Ubuntu provided a working in-kernel driver for the AWUS036ACH.
2. No conflicting Realtek DKMS driver was installed.
3. Firmware version `52.14.0` initialized successfully.
4. The adapter operated through USB at `5000` Mbit/s.
5. USB runtime autosuspend was disabled during the test.
6. The driver unloaded and reloaded without affecting the internal Wi-Fi card.
7. The interface name remained stable while the PHY number changed.
8. The module matched the running kernel and was signed.
9. Installing a third-party driver was unnecessary at this stage.

## Conclusion

The in-kernel `rtw88_8812au` driver passed the baseline verification checks.
It should remain the active driver unless a later experiment demonstrates a
specific unsupported capability or reproducible defect.
